# Secrets management: passwords, API keys, tokens, and certificates.
Q: API keys and passwords should be stored in:
+ An approved secrets manager or password vault
- Source code
- A spreadsheet on the shared drive
- Chat messages

Q: A secret accidentally committed to a code repository must be:
+ Revoked and rotated, even if the commit is deleted
- Deleted from the latest version only
- Left alone if the repo is private
- Renamed

Q: Sharing a service account password over email is:
+ Not allowed; use the approved sharing feature of the vault
- Fine if marked confidential
- Required
- Fine with a typo

Q: Secrets should be rotated:
+ On a schedule and whenever they may have been exposed
- Never
- Only when someone leaves the company
- Only after a breach is public

Q: A canary token is:
+ A decoy credential or link that alerts Security when someone uses it
- A coin for the vending machine
- A password hint
- A bird-watching app

Q: Hard-coding a database password in a script on a shared server is:
+ Not allowed; use secrets management
- Fine for automation
- Required
- Secure if the file is hidden

Q: Screenshots shared in tickets or chat should be checked for:
+ Visible secrets such as tokens, passwords, or keys
- Font choices
- Colors
- Typos only

Q: A ".env" file containing secrets should be:
+ Kept out of version control and protected
- Committed so others can use it
- Emailed to the team
- Posted on the wiki

Q: When a developer leaves the team, secrets they had access to should be:
+ Reviewed and rotated as needed
- Kept the same
- Given to their replacement by email
- Deleted from the vault

Q: Secrets found on public paste sites or code repositories should be:
+ Reported to Security immediately
- Tested to see if they work
- Shared with coworkers
- Ignored

Q: Printing secrets in application logs is:
+ Not allowed
- Useful for debugging forever
- Required by auditors
- Harmless
